# Structured logging, correlation, and redaction contract

**Status:** application boundary implemented and non-production (`staging` runtime label) configuration source-controlled. Do not claim collector redaction, ingestion, telemetry, alerts, or routing are active until deployed non-production tests prove them.

## Event envelope

Emit one JSON object per event. Request-completion events use these names and types:

| Field | Required | Rule |
|---|---:|---|
| `timestamp` | yes | UTC RFC 3339 instant generated by the service |
| `level` | yes | `DEBUG`, `INFO`, `WARN`, or `ERROR` |
| `service.name` | yes | Low-cardinality service name (`rotrack-api` or `rotrack-frontend`) |
| `deployment.environment` | yes | Exactly `staging` or `production` |
| `service.version` | yes | Non-secret immutable release ID |
| `event.name` | yes | Stable allowlisted name, e.g. `http.request.completed` |
| `correlation.id` | yes for HTTP | Opaque random ID validated/generated at the edge/API |
| `http.request.method` | yes for HTTP | Allowlisted HTTP method |
| `http.route` | yes for HTTP | Matched route template, never raw path/URL/query |
| `http.response.status_code` | yes for completed HTTP | Integer status |
| `http.response.status_class` | yes for completed HTTP | `2xx`, `3xx`, `4xx`, or `5xx` |
| `duration_ms` | yes for completed HTTP | Non-negative server elapsed milliseconds |
| `error.code` | on known failures | Stable application/security code only, such as `ACTIVE_SESSION_EXISTS`; no message/detail |
| `exception.type` | on unexpected server failure | Allowlisted class/category without message |
| `actor.id_hash` | optional | Environment-scoped pseudonymous hash; never raw JWT `sub` |
| `resource.id_hash` | optional | Environment-scoped pseudonymous hash only when operationally necessary |
| `cloud.instance.id` | optional | ACA replica/runtime instance identifier only when the platform exposes a value approved as non-secret |
| `trace.id` / `span.id` | optional | Valid telemetry identifiers; never derived from user input |

Do not add arbitrary maps to this envelope. Fields and values are allowlisted; unknown fields are dropped before export. Metrics dimensions use only environment, service, release, route template, method, status class/code, error code, and exception fingerprint. Correlation, actor, resource, trace, and runtime-instance IDs are searchable fields but never metric labels.

A safe request event example uses synthetic values only:

```json
{"timestamp":"2030-01-01T00:00:00Z","level":"INFO","service.name":"rotrack-api","deployment.environment":"staging","service.version":"rotrack-20300101-1","event.name":"http.request.completed","correlation.id":"01ARZ3NDEKTSV4RRFFQ69G5FAV","http.request.method":"PUT","http.route":"/api/v1/time-entries/{id}/stop","http.response.status_code":200,"http.response.status_class":"2xx","duration_ms":42}
```

## Correlation ID rules

- The trusted edge or API generates at least 128 bits of randomness when no ID exists.
- Accept an inbound correlation ID only from a trusted proxy/header path and only when it matches `^[A-Za-z0-9_-]{16,64}$`; otherwise replace it. Do not reflect arbitrary input.
- Return the validated/generated ID in a dedicated response header once the application contract implements it. CORS must expose only that header as required.
- Preserve the ID across internal calls and frontend error reports, but never use it as authentication, authorization, or a user/session identifier.
- Emit exactly one request-completion event with route, status, and duration. Avoid separate start/end events unless tracing requires them.
- Do not include correlation IDs in user-visible error messages. They may appear as a separate support reference after the API contract explicitly adds it.

Until correlation propagation is implemented and tested, monitoring must correlate by environment, release, normalized route, and time. It must not substitute email, JWT subject, storage key, session ID, or a raw time-entry UUID.

## Safe identifier rules

Raw user UUIDs, Supabase auth IDs, time-entry UUIDs, emails, usernames, and note IDs are not logging-safe merely because they are identifiers.

When a user/resource join is essential for abuse or incident diagnosis:

1. Normalize the canonical UUID in memory.
2. Compute an HMAC with a secret dedicated to that environment and logging purpose.
3. Emit a short versioned representation such as `h1:<base64url digest>` with at least 128 retained bits.
4. Keep the HMAC key out of application logs, frontend code, monitoring configuration exports, and evidence. Rotate it under an approved incident/privacy procedure.
5. Never hash low-entropy email, username, IP, note text, or query values; hashing those does not make them safe.

Prefer omission over hashing. Staging and production keys must differ so records cannot be joined across environments.

## Mandatory redaction and drop rules

Drop these at the application logger **and again** at the collector/monitoring provider:

- `Authorization`, `Proxy-Authorization`, bearer/JWT/API tokens, JWKS/auth payloads, token claims, refresh/access/ID tokens;
- `Cookie`, `Set-Cookie`, CSRF values, Supabase session/storage state, localStorage/sessionStorage contents, browser storage keys;
- all URL query strings and fragments, even on public routes; log only the matched route template;
- database/JDBC URLs, usernames/passwords, credentials, secret-manager values/references that embed values, service-role keys, public/private signing keys, CA contents;
- request and response bodies, form values, multipart parts, GraphQL variables if later introduced, and serialized DTO/entity objects;
- note/session-label content, note titles/content, private reflections, rich-text JSON/HTML/plain text, autosave payloads, dashboard/session payloads;
- raw headers except an explicit low-risk allowlist; never use an automatic “all headers” mode;
- raw authentication/authorization objects, principals, JWT claims, Supabase SDK objects/errors, email addresses, usernames, raw user/resource UUIDs;
- SQL text/bind parameters, ORM entity dumps, connection strings, stack traces containing payload values;
- frontend console messages, DOM/session replay, input values, screenshots, network bodies, and source snippets that can contain user data.

Redaction must replace a forbidden field with omission, not a reversible mask. A value such as `Bearer [REDACTED]` still reveals that an unsafe logging path ran; drop the field and alert on the redaction counter. Keys are matched case-insensitively and recursively before serialization/export.

## Error and stack policy

- Expected `4xx` events log status, normalized route, duration, and stable safe error code. They do not log exception stacks.
- Unexpected `5xx` events log an allowlisted exception type/fingerprint and correlation ID. Exception message and stack are retained only if a scrubber proves forbidden content is absent; the safer initial production setting is type/fingerprint without message and a restricted, scrubbed stack in the error-monitoring provider.
- Readiness failures log `database.readiness.failed`, duration, runtime instance/release, and a coarse reason (`timeout`, `unavailable`, `unknown`). Never log JDBC/SQL/provider messages or dependency host details.
- Authentication failures log status and coarse safe reason (`missing_credentials`, `invalid_token`, `insufficient_authority`) after review. They never log token syntax, claims, subject, issuer value, raw IP, or security exception message.

## Frontend contract

Frontend error events use environment, release, route template, scrubbed exception fingerprint/type, coarse browser/runtime version, and a validated API correlation ID when available. They must strip:

- full `window.location` (query and fragment), referrer query, navigation state;
- React props/state, component input values, console breadcrumbs, network request/response data;
- Supabase client/session/auth objects and browser storage;
- user identity, dashboard/time-entry responses, note/session-label content, or reflection content.

Session replay and automatic DOM/network instrumentation are disabled. Source maps are uploaded as restricted release artifacts and are not publicly exposed by the monitoring provider.

## Enforcement and verification

Before enabling non-production ingestion:

1. Unit-test the structured encoder with sentinel values for every forbidden category and assert none appear in serialized output.
2. Integration-test representative success, validation, auth failure, ownership `404`, conflict `409`, unexpected `500`, and readiness `503` requests.
3. Search captured events for sentinel bearer/cookie/query/database/body/note/reflection/auth payload values. The test fails on any match.
4. Verify every HTTP completion has correlation ID, normalized route, status, and duration, and has no raw path/query.
5. Verify collector rules drop forbidden mixed-case and nested keys and increment a restricted redaction/drop counter.
6. Verify non-production events cannot appear in production projects, dashboards, alerts, or exports.
7. Repeat the capture test after logging framework, security, exception handler, ORM, HTTP client, Supabase SDK, or monitoring-agent upgrades.

Production ingestion remains blocked until this evidence and provider access/retention review pass. Never validate redaction with real credentials or private content; use unmistakable synthetic sentinels.
